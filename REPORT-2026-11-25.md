## 1. Why latency is ~5 ms (no change made)

Measured URLLC ping: min/avg/max 3.1–5.0 / 5.3–6.1 / 6.7–7.1 ms over several runs.

- **Wrong yardstick.** The 3GPP URLLC target (TS 38.913) is 0.5 ms one-way over the radio.
  Ping is a full round trip through gNB, GTP-U, UPF and ext-dn.
- **Radio is configured for eMBB.** `gnb.conf`: 30 kHz SCS (0.5 ms slots), TDD period 5 ms
  (7 DL + 1 special + 2 UL slots). An uplink packet waits for a scheduling request and a
  grant in a 2-slot UL window, which gives a floor of about one TDD period (~5 ms).
- **5QI 7 is not a URLLC 5QI** (TS 23.501 table 5.7.4-1: non-GBR, 100 ms budget; the
  delay-critical ones are 82–86).
- **OAI does not differentiate slices in the RAN.** The gNB creates a DRB per session
  (5QI 9 and 5QI 7 are logged) but the MAC scheduler passes the 5QI only to external
  policies, and reads it from the UE's first data bearer. There is no RAN slicing.
- **The "URLLC is faster" numbers from 2026-10-28 were noise**: eMBB's average was pulled up
  by one 142 ms first packet; both minimums were ~5 ms.
- **Not done, but would help**: TDD period 2.5 ms (`dl_UL_TransmissionPeriodicity = 5`,
  3 DL / 1 UL slots) should give ~2.5–3 ms; sub-millisecond RTT is not realistic with RF-sim.

## 2. Why the AMBR was not enforced

Chain of causes, found one at a time:

1. **Only downlink had ever been tested** (`iperf3 -R`). Uplink added: `./lab.sh iperf <i> <embb|urllc> [secs] [dl|ul]`.
2. **SMF flag.** The SMF signalled the AMBR to the UE (NAS) but its UPF config showed
   `enable_qers: No`, so the PFCP session establishment carried no QER. Fix: `enable_qers: yes`
   under `smf.upfs`. The SMF matches that per-UPF config by *host*, and the NRF-discovered UPF
   is keyed by IP, so a second entry `host: 192.168.77.134` is needed too.
3. **The simple-switch UPF still did not police** (downlink 328 Mbit/s, uplink 159 Mbit/s after
   step 2, raw: `lab/run/tests/ue1-iperf-urllc-{dl,ul}-qer.txt`). The UPF binary contains the QER
   enforcement (`QERProgram`, `qer_tc_kernel`) only in its **eBPF datapath**.
4. **Enabling the eBPF datapath** (`enable_bpf_datapath: yes`, `enable_qos: yes`) required, in order:
   - **N3 and N6 on separate interfaces.** With one `eth0` for both, the second XDP attach fails
     (`XDP program already attached`) and the UPF crashes. New docker network `oailab77-n6`
     (192.168.77.192/26, bridge `br-oailab77n6`); UPF `eth0` = N3/N4 (.134), `eth1` = N6 (.194);
     ext-dn moved to the N6 network only (.195, so `EXTDN_IP` changed).
   - **GRO on the host-side veth of N6.** XDP redirect into a veth needs NAPI on the receiving
     end. Without it the uplink packets reached the UPF `eth0` but never left `eth1`
     (per-hop counters). Root helper: `sudo ./lab.sh n6-gro` after every `cn-up`.
   - **N3 MTU 1600.** The eBPF UPF cannot fragment; GTP-U adds ~44 bytes, so full-size
     (1500 B) packets were dropped. Ping payloads up to 1400 B passed, 1472 B failed.
   - **ext-dn TX checksum offload off.** Partial TCP checksums are lost across the XDP redirect
     and the UE drops the packets (`TcpInCsumErrors` rose during every iperf attempt, while
     ICMP worked). In the compose entrypoint: `ethtool -K eth0 tx off tso off gso off` (inside
     my own container's netns only).
5. **Result with the eBPF UPF: still not enforced.**

   | Slice | Downlink | Uplink | Intended |
   |---|---|---|---|
   | eMBB | 1.2 Mbit/s | 50.1 Mbit/s | AMBR 10 Gbit/s |
   | URLLC | 1.2 Mbit/s | 50.2 Mbit/s | AMBR 50 Mbit/s |

   Raw: `lab/run/tests/ue1-iperf-*-ebpf.txt`. UPF log: both PDU-session HTB classes are created at
   10 Gbit/s (`Create PDU Session Class 1:2 with rate: 10000000`), so the 50 Mbit/s never
   reaches the rate setup; downlink falls into the UPF's default class
   (`Rate: 1024 kbit and Ceil: 2048 kbit`), hence ~1.2 Mbit/s on both slices; the HTB is on
   `eth0` egress so uplink is not shaped at all, and the ~50 Mbit/s uplink on *both* slices
   comes from something not identified yet.

## 3. Incidents (all inside my own project)

- **Core containers could not talk to each other.** Docker's per-network accept rules for
  `br-oailab77` were missing from the host FORWARD chain (policy DROP). `lab.sh down` + `cn-up`
  recreated the network and Docker re-added them. Cause of the loss unknown; nothing of anyone
  else's was touched.
- **Stale PDU sessions** after the UE died ungracefully: the SMF rejected the re-registration
  (`Failed to add PDU Session ... invalid Id`). Restarting the core containers in place fixed it.
- **Lesson:** do not stop a hung foreground test by killing its task; the UE's in-netns tmux
  server went away at that moment. iperf in `lab.sh` now has a hard `timeout`
  (`--connect-timeout` must not be used: it breaks iperf3's control channel here).

Recommendation: option 2 for a working 50 Mbit/s slice, option 1 only if the 3GPP mechanism itself matters.
